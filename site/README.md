# Origin HeartGold guide website

The player website: the quest guide, Pokédex, locations, items, moves, trainers and move tutors,
plus a PDF of the quest guide. Built with [Astro Starlight](https://starlight.astro.build) and
published at https://originheartgold.github.io/ by `.github/workflows/site.yml` (see [Publishing](#publishing)).

## Where the content comes from

| Site content | Source of truth | Generated by |
|---|---|---|
| Quest guide pages (`src/content/docs/guide/`) | quest entries in `guide/NN-*.md`, chapters (order, walkthrough, what each step opens or closes) in `guide/chapters/*.toml`; both hand-written | `work/tools/site/sync_guide.py` |
| Game data (`src/data/*.json`) | the released English ROM (data and text; see [below](#which-game-the-data-describes)), curated attributed reference facts | `work/tools/site/export_data.py` (reuses `work/tools/docs/gen_docs.py`) |
| Room names ("Celadon Game Corner") | map data + `work/docs/place_names.json` | `work/tools/docs/places.py` |
| PDF (`public/downloads/`, not committed) | `guide/*.md` | `work/tools/site/build_pdf.py` (Pandoc + Typst) |
| Patch page data (`public/patch/`, not committed) | the newest GitHub release and its `latest.json` | the site workflow; `work/tools/site/patch_manifest.py` makes `latest.json` |
| Home, About, Contribute, Patch pages | `src/content/docs/*.md(x)` | hand-written |
| Pokémon / location / item / move / trainer / tutor pages | `src/pages/**` (templates) | Astro, from `src/data` |

### Quest guide chapters

The guide is ordered by what unlocks when. `guide/NN-*.md` only stores the quest entries (one H2 each, with a stable
`q-NNNN` id); the site never shows those files as pages. `guide/chapters/NN-slug.toml` places every quest in exactly one
chapter and holds the chapter's walkthrough: each step says what it opens (`unlocks`) and what it closes for good
(`closes`, shown as a red Warning box that hides itself once the quests are done or filtered out). The format and rules
are in `work/notes/guide_chapters_plan.md`. `python3 work/tools/site/chapters.py` validates the files and
`work/tools/site/test_chapters.py` tests the rules; `sync_guide.py` refuses to run when they fail. Old region URLs
(`/guide/pewter-to-vermilion/#anchor`) forward to the right chapter through `src/generated/guide_legacy.json`;
`relink_guide.py` rewrites links to old pages inside the committed data and pages.

`work/tools/site/quest_ledger.json` keeps quest identities (id, source, legacy Done-tick keys). The curated ledger of
rc8 was never committed and is lost; the file was restored from an unreachable git blob (identities only, every stage
`unknown`), and the stage data now lives in the chapter files.

Never edit the generated files by hand: change the source and regenerate. `src/data` is
committed, because CI has no ROM. `src/content/docs/guide` is not committed: CI and
`build.py` regenerate it from `guide/*.md`.

Author workbooks are reconciled by `work/tools/site/reconcile_references.py`; `reference_content.json` holds curated English notes and scoped audit corrections. `reference_facts.json` and `reference_coverage.json` are generated. The source report at `/reference-sources/` distinguishes source accounting from runtime verification. Do not edit generated reference facts directly.

## Availability labels

Keep all named Pokémon, forms and items in the reference listings. The reviewed
`work/tools/site/not_in_game.json` and `items_not_in_game.json` lists provide the
`unavailableReason` exported with each affected entry. They label normal-play
availability; they must not remove reference pages or imply that an entry cannot
be added with an editor or generator. An unknown source is a separate status.
Listings show all entries by default and offer an availability filter.

## Everyday tasks

### Team Builder

`/team-builder/` is a six-member playthrough planner inspired by
[richi3f's Pokémon Team Planner](https://github.com/richi3f/pokemon-team-planner).
The implementation uses the guide's existing data and artwork helper; it does not
import the upstream planner's game data or assets.

Teams use unique Origin HeartGold record IDs so forms remain distinct. The team is
saved locally under `ohg-team-builder-v2` (team, optional battle sets, Battle check
opponent; `src/lib/team-builder-state.mjs`). The older `ohg-team-builder-v1` key is still
read when no v2 state exists and is kept up to date. Links stay compatible: `#team=3,94,196`
still loads, and sets are appended only when changed (`&sets=3.L50.NModest_94.I239`).
An explicit shared team takes precedence over browser storage. Nothing is uploaded.

Battle check (`src/lib/battle-check.ts`) is a damage calculator view built on
`src/lib/calc` (see its README). Its code, the engine, `team-builder/calc-data.json` and
`team-builder/battle-data.json` (trainer teams in route order and learnsets, from
`src/lib/battle-check-data.mjs`) load only when it is opened, so the planner's first load
does not include them. Trainer pages link to it with `/team-builder/#battle=<trainer id>`.
Its browser regression is `site/tests/team-builder-calc-browser.mjs` (same setup as below).
The catalog defaults to documented acquisition sources; other availability categories
remain selectable and labeled.

`src/lib/team-builder-data.mjs` follows incoming evolution links and verified held-item
transformations to include all earlier stages, without including sibling evolutions.
Each member's acquisition guide is built into `team-builder/pokemon/<id>.json` and
loaded when selected. Catch values, encounter percentages, contest weights, unknown
Safari odds, gifts, quest restrictions, evolution priority notes and calendar forms
retain their existing meanings. Unverified or unavailable methods are labeled.

Run from the repository root, using installed dependencies:

```sh
python3 work/tools/site/sync_guide.py
GUIDE_BASE=/poke/ npm --prefix site run build
GUIDE_TEST_DIST=1 npm --prefix site test
python3 work/tools/site/check_site.py --base /poke/
GUIDE_BASE=/poke/ npm --prefix site run preview -- --host 127.0.0.1 --port 4346
PLAYWRIGHT_MODULE=/absolute/path/to/existing/playwright/index.mjs node site/tests/team-builder-browser.mjs
```

The browser regression uses an isolated browser, blocks external requests, and checks
team limits, filtering, persistence, sharing, error recovery, keyboard input and
responsive layouts. Screenshots and logs go to ignored `work/build/team-builder-qa/`.

The desktop planner places the catalog beside a field guide. Mobile uses Find Pokémon /
Field guide tabs. Evolution cards open each stage's catch locations; full acquisition
conditions, alternative evolution routes and base stats are expandable.

### Base stat and type changes

`/stat-changes/` and `/type-changes/` (and the "Official games" notes on each Pokémon page) are computed
at build time by `src/lib/species-changes.ts` from `src/data/species.json` and
`src/data/official_species.json`. That file lists the official values (the latest official games) only
for entries that differ from the hack. Its Generation I–IV and HeartGold-form entries come from the US
ROM plus the later official changes in `work/tools/site/species_comparisons.py`
(`--check-us-rom` / `--import-us-rom`); later species and forms are curated (`"source": "official"`).
`test_species_comparisons.py` fails when an entry no longer differs from the game data.

### Shared time, encounter and catch labels

`TimeHints.astro` renders sun/moon symbols and dotted-underlined time labels for
encounter condition text. Hover, keyboard focus or tap opens a shared description;
Escape or an outside tap dismisses it. The tooltip stays within the viewport, including
inside scrolling encounter tables. A native title provides a no-JavaScript fallback.

Use `<CatchDifficulty value={catchRate} />` (or `formatCatchHint` in dynamic views)
for capture information. A visible label and five-bar meter show relative catch difficulty (more bars = harder).
These guide-defined bands compare base values: Very easy 200–255, Easy 120–199,
Moderate 60–119, Hard 30–59, Very hard 0–29. They are not game rules or capture
probabilities. Unknown values show an empty meter and an Unknown label. The raw
base value stays in the popup with an explanation of HP, status and ball effects.

Use `<EncounterHints text={method} />` for encounter methods,
`<TimeHints text={condition} />` for time-only conditions, and
`<TimeHints text={condition} context="evolution" />` for evolution requirements.
Dynamic views use `formatTimeHints` from `src/lib/time-hints.mjs` and
`formatEncounterHints` from `src/lib/encounter-hints.mjs`. Encounter labels cover
land, water, rods, trees, rocks, radio, swarms, Safari, contest and calendar encounters.
Only annotate method fields, never named moves or items in ordinary prose. The shared header
initializes the delegated interaction, so it also handles content loaded later.
Apply it only to condition text, never indiscriminately to names such as Morning Sun.

Encounter Day is 10:00–19:59; evolution Day is 04:00–19:59. Evening is described as
part of the encounter Day window, without inventing a separate encounter table.
The component is used by the planner, Pokémon wild encounters/evolutions, location
encounter tables, calendar encounters and wild-held-item locations.

### Which game the data describes

`site/src/data` (and `work/docs/`) describe the game players get from the **newest published release**: the
exporter reads that release's ROM, so every fix the release turns on shows up (Boldore's Lv 35 evolution, the
Blackthorn tutor's Play Rough, the trainer EVs of a release with `trainer-ev-order`, an added ability name) and
disabled fixes stay out. Nothing is patched by hand on the site side.

- The ROM is chosen with `--rom` (or `OHG_DOCS_ROM`), the same for `export_data.py`, `gen_docs.py` and
  `build.py --content`: `release:latest` (the default: the highest `work/release/<tag>/` with a `latest.json`),
  `release:<tag>`, `build` (the unreleased standard build, for a local preview only), `cn` (the untouched Chinese
  hack) or a `.nds` path. A release ROM is rebuilt from `work/release/<tag>/*.xdelta` and the clean USA ROM into
  `work/build/release-roms/<tag>.nds` (gitignored) and must hash to the `patched_sha1` of its `latest.json`.
- `meta.json` records the ROM (`rom`: label, kind, tag, SHA-1); `/reference-sources/` shows it.
  `export_data.py --check` fails when the committed data was exported from another ROM than the one requested, and
  `site/tests/reference-data.test.mjs` fails unless the data names a release.
- Names, descriptions and dialogue options are the ROM's own English text. Chinese names (`zh`) and the hack-finding
  comparisons still come from the translation workspace and the untouched Chinese ROM. Per-field sources and the
  reasoning: `work/notes/site_export_built_rom.md`.
- **At each release** (RELEASING.md, section 1 step 6): once `work/release/<tag>/latest.json` exists, run
  `python3 work/tools/site/build.py --content --rom release:<tag>`, review the data diff (every change should
  come from a fix or text change of that release) and commit `site/src/data` and `work/docs` with the release. Never
  commit data exported from `build` or `cn`: the site must not show a game players can't download yet.

### After a release: the changelog page

`/changelog/`, the home page's release line and the patch page's version line read `src/data/releases.json`
(player-facing summaries, newest first, written by hand from `CHANGELOG.md`: plain language, no decision ids or
tooling). Add the new release at the top and its contributors to `src/data/contributors.json`
(`{"1.0.0-rc9": ["name", ...]}`; an empty list shows no "Thanks to" line). `tests/changelog.test.mjs` fails until
every version in `CHANGELOG.md` is there (rc1 and rc2 were never released: rc3 lists `includes`; rc3 and rc4 were
shared as patch files, `"github": false`, with a note instead of a release link).

## Writing guide entries

- One `## Place: what happens (tags)` heading per quest. The place before the colon links the quest
  to its location page; with `→` or ` / ` between places, each place gets a link. Rooms and sub-areas
  that have no page of their own (Pokémon Tower, Silph Co., Sea Cottage…) are mapped in
  `work/tools/site/area_aliases.json`; `sync_guide.py --unmatched` lists headings with no link.
- A phrase in the parentheses becomes a filter only when it stands alone between commas or semicolons
  and the restriction covers the **whole** quest: "Charmander starters (only)", "non-Pikachu starters",
  "male players", "post-game", "after the final Hall of Fame", "after Lance's visit". If only a reward
  or a step differs, say so in the body and keep it out of the heading ("Charizardite for Charmander
  starters" does not hide the quest). "Post-game" means after the **final** Hall of Fame entry; write
  "after your first Hall of Fame" for things that open with Johto. "Missable" and "one chance" add a
  badge but hide nothing. Changing a heading changes its URL: update links to it.
- When the heading can't say it, add explicit metadata on the line right under the heading. It overrides
  what is read from the heading and is left out of the site page and the PDF:
  `<!-- quest: kind=main; id=ch07-giovanni; places=cerulean-cave; starter=any; gender=any; postgame=no -->`.
  Every quest needs `kind=main` (story, badge progression and their walkthroughs) or `kind=side`
  (optional activities, rewards and extras). Classify from the entry's content, including conditional
  story routes; a reward alone doesn't make a story quest optional. Mixed entries covering story
  progression and optional rewards use `main`. Other keys are optional.
  `starter` takes `any`, a comma-separated list or `non-Pikachu`; `gender` takes `any`, `male` or `female`;
  `postgame` and `missable` take `yes` or `no`; `places` takes area slugs or names (`none` for no link).
  `id` is a stable key for the reader's "Done" tick, so the tick survives a heading rename; keep ids unique.
- Quest type and Progress filters combine with starter, gender and Hide finished and persist between
  chapters. Progress offers all stages, before post-game, and post-game only. Mixed entries with earlier
  steps aren't post-game-only; their text explains later unlocks. Linked quests stay visible even when
  they don't match the filters. Existing post-game checkbox preferences migrate to the Progress filter.
- Each entry follows the same pattern: where and when, any **Warning:** before the step it applies to,
  numbered steps, the reward and whether it repeats, exact links (`file.md#heading`) to the quests it
  depends on, and the folded `*Source:*` line last.
- Link to the website's reference pages with a root-relative path: `[Move tutors](/tutors/)`,
  `[Mew](/pokemon/mew/)`, `[Charizardite](/items/charizardite/)`, `[Cerulean Cave](/locations/cerulean-cave/)`,
  `[trainers](/trainers/)`, `[moves](/moves/)`. Use the slug from the page's URL. There is no separate
  trades page: trades and gifts are on the location page (`/locations/<slug>/#special`), shops at `#shops`.
  `sync_guide.py` rewrites these for the site's base path; the PDF turns them into links to the published
  site (`GUIDE_PUBLIC_URL`) or, without it, plain text. `check_site.py` reports broken ones.
- Pictures go in `guide/images/` (lower-case, hyphenated names, e.g. `viridian-forest-honey-tree.jpg`) and are
  linked as `![what the picture shows](images/<name>.jpg)`. The alt text says what the player should look for.
  `sync_guide.py` copies them next to the site pages (Astro converts them to WebP) and the PDF embeds them.
  Remove EXIF data from phone photos before adding them: it can include the location and the device.
- Give directions with landmarks ("a few steps east of the Pokémon Center door"), never coordinates.
  `python3 work/tools/docs/landmarks.py near "Celadon City" 1236,238` turns a coordinate into
  landmarks; `python3 work/tools/docs/scriptdump.py <file>` shows an event script with its dialogue.
- Script files, flags and line numbers go only in the entry's last line, `*Source:* …`. The site folds
  it into a "Technical source" box that players never see: it stays in the HTML but is hidden by CSS and left out of
  the site search, and the PDF leaves it out. To see these boxes, open any page once with `?tech=1` (remembered in
  your browser; `?tech=0` hides them again). Any other technical reference on a page gets the same treatment
  with `class="tech" data-pagefind-ignore="all"`.

## The patch page (/patch/)

`src/content/docs/patch.mdx` with `src/components/Patcher.astro` lets players patch their own HeartGold (USA)
dump in the browser: they drop (or choose) a `.nds` or a `.zip` holding it, and the rest runs on its own.
Nothing is uploaded: the page unpacks a `.zip` (`patch-tool/zip.js`: stored/deflate, Zip64, via the browser's
`DecompressionStream`; it picks the `.nds` whose CRC32 is `C180A0E9`, else the biggest), hashes the file
(CRC32 must be `C180A0E9`), downloads the patch, applies it with xdelta3 compiled to WebAssembly in a Web
Worker, checks the result's SHA-1 and offers it as `Origin_HeartGold_v4.0.3_EN_<tag>.nds`. The site never
serves the base ROM.

- **Code:** `public/patch-tool/` (`worker.js`, `xdelta-run.js`, `hash.js`, `zip.js`) is ours. `public/vendor/xdelta-wasm/`
  holds the unmodified `xdelta3.js`/`xdelta3.wasm` from [xdelta-wasm](https://github.com/kotcrab/xdelta-wasm)
  (Apache-2.0; source, commit and hashes in its `SOURCE.txt`). No CDN is used.
- **Data:** `public/patch/latest.json` (`{available, tag, file, size, patched_sha1, release_url, prerelease}`)
  and the `.xdelta` beside it. Browsers can't download GitHub release assets cross-origin, so the site serves
  its own copy. In CI, the workflow takes the newest published release (pre-releases included), downloads its
  `latest.json` asset and the `.xdelta` it names, and checks the SHA-1 and size. Without a usable release it writes
  `{"available": false}`, warns in the run and the page shows only the manual steps. `public/patch/` is
  in `.gitignore`: never commit a patch.
- **Cutting a release:** run `python3 work/tools/site/patch_manifest.py <tag>`. It checks
  `work/release/<tag>/` (one `.xdelta`, its SHA-1 and the "Result ROM SHA-1:" line in `README.txt`) and writes
  `work/release/<tag>/latest.json` (`{tag, file, size, sha1, patched_sha1}`). Upload it with the release:
  `gh release create <tag> --prerelease work/release/<tag>/{*.xdelta,README.txt,latest.json}`
  (or `gh release upload <tag> work/release/<tag>/latest.json`, then rerun the Website workflow).
- **Redeploys:** publishing a GitHub release starts the workflow, which re-runs itself on the default branch
  (only the default branch deploys), so `/patch/` serves the new patch.

Local testing (no network):

```sh
python3 work/tools/site/patch_manifest.py --site  # newest work/release/<tag>/ patch + README SHA-1
python3 work/tools/site/patch_manifest.py --none  # or: test the "not available" fallback
(cd site && npx astro dev)                        # then open http://localhost:4321/patch/
node work/tools/site/test_patcher.mjs --xdelta3   # runs the vendored wasm on work/rom + the newest release
node work/tools/site/test_patcher.mjs --zip a.zip  # unzips + hashes like the page (zip your ROM outside the repo)
```

`test_patcher.mjs` needs the USA ROM in `work/rom/` and writes nothing: it hashes the patched ROM as it streams
and compares it with the release README's SHA-1 (and with native `xdelta3 -d` when given `--xdelta3`).

## Publishing

The workflow builds on every push to `main` that touches `site/`, `guide/` or `work/tools/site/`, and on every published release,
checks that the guide pages are in sync and that no link is broken, and deploys:

- **The site, at the host root** https://originheartgold.github.io/ (`GUIDE_BASE=/`). The `deploy-root` job
  force-pushes the build, as one orphan commit by `github-actions[bot]`, to the `main` branch of the user-site repo
  `originheartgold/originheartgold.github.io`, which serves it with GitHub Pages (Deploy from a branch: main, / (root)).
  It authenticates with a write deploy key on that repo whose private half is the Actions secret `PAGES_DEPLOY_KEY`
  in this repo. The build adds a root `robots.txt` (allow all, a `Sitemap:` line; no `Disallow: /preview/`, the preview pages are `noindex`) and
  `.nojekyll` (Jekyll would drop `_astro/`). The tester preview is under `/preview/`.
- **Redirects at the old address** https://originheartgold.github.io/origin-heart-gold-EN-translation/, still this
  repo's GitHub Pages (**Settings → Pages → Source: GitHub Actions**). `work/tools/site/redirect_site.py` turns the
  build into a stub per page (canonical to the new URL, `noindex`, meta refresh and a `location.replace` that keeps
  the query and `#anchor`), a `404.html` that sends any other old path to the same path at the root, and copies of
  every non-HTML file (patch, PDF, patch tool, save editor files) so old download links keep working. The `deploy`
  job publishes it only after `deploy-root` has pushed and the root answers, so the old address never points at an
  empty site.

The repository URL comes from the repository; the site URL is set in the workflow (`site.config.mjs` holds the local
fallbacks). The move and its checklist: `work/notes/root_site_move.md`.
Search engine ownership tags (W-011): set the Actions variables `GUIDE_GOOGLE_VERIFICATION` (Search Console's
HTML-tag `content`) and `GUIDE_BING_VERIFICATION` (Bing's `msvalidate.01` value); production builds then carry the
`google-site-verification` and `msvalidate.01` meta tags on every page. Preview builds never do.

A local build with the production URLs, from the repository root (W-056):

```sh
python3 work/tools/site/sync_guide.py
cd site && GUIDE_SITE_URL=https://originheartgold.github.io GUIDE_BASE=/ \
  GUIDE_REPO_URL=https://github.com/originheartgold/origin-heart-gold-EN-translation npm run build
```

Add `GUIDE_PREVIEW=1 GUIDE_BASE=/preview/` for the tester preview. A git worktree has no `node_modules`: link both
the site's and the save editor's from the main checkout (both are ignored), or `prebuild` stops with "TypeScript is not
installed in work/save-editor/node_modules":
`ln -s <main checkout>/site/node_modules site/node_modules` and
`ln -s <main checkout>/work/save-editor/node_modules work/save-editor/node_modules`.

Bug reports, screenshots and edit suggestions arrive as GitHub issues through the forms in
`.github/ISSUE_TEMPLATE/`; every page links to them with the page filled in.

## Save editor and navigation

The main destinations (Walkthrough, Pokédex, Trainers, FAQ, Save editor and the "Get the patch" button) are one list,
`src/lib/primary-nav.ts`, rendered by `PrimaryNav.astro` in three places: in the header from 78rem up; in a Menu
popover on pages without a sidebar (home, 404), with the theme choice and the social links; and at the top of the
phone navigation drawer (`Sidebar.astro`). The current section gets `aria-current`. Keep the list short: the header has
room for about six items at 78rem.

The editor uses the standalone `sv` implementation in `work/save-editor/`, with its own full-width layout and a Guide link back to the site. Astro bundles its TypeScript and stylesheet directly. `src/pages/save-editor/index.astro` dresses the shell as part of the site: title, description, canonical, social tags and JSON-LD like the other pages, the site wordmark with an `h1`, the site's font stack (no Google Fonts), a backup note and the footer text. Its theme toggle stores under the site's `starlight-theme` key (`data-theme-key` on `<html>`), so the theme follows the rest of the site; the standalone editor keeps `ohg-editor-theme`.

On desktop, the header hamburger collapses the guide sidebar and remembers that choice. On small screens, Starlight's existing hamburger opens the navigation drawer. All links respect `GUIDE_BASE` for GitHub Pages deployment.

### Accessibility checks

- Tables need a name. Components and pages give theirs a `<caption class="sr-only">`; Markdown tables get
  `aria-label` from the heading before them (`src/lib/rehype-a11y.mjs`, a Sätteri hast plugin set as
  `markdown.processor` in `astro.config.mjs`). `ohg.js` makes a table's scroll panel a named, focusable region only
  while it really scrolls sideways.
- Chinese and Japanese text needs a `lang`: the same plugin wraps it in Markdown; in templates use `<Cjk text={…} />` or
  `<span lang="zh-Hans">`.
- Trainer teams and encounter lists (`.stack-table`, with `data-label` on each cell) turn into one card per row below
  40rem.
- `tests/a11y.test.mjs` scans every built page (with `GUIDE_TEST_DIST=1`): images without `alt`, ARIA names on elements
  that can't have one, duplicate ids, unnamed tables, row headers without `scope`, untagged Chinese/Japanese text and the
  ↗ "leaves the site" arrow on internal links. It also checks one `h1` and the main navigation on sample pages.
- Astro caches rendered Markdown: after changing the plugin, build once with `npm run build -- --force`.

The reference pages share the artwork URL helper in `work/save-editor/src/ui/artwork.ts`; builds do not download artwork.

### Page weight

- Pokémon images: small images (`<PokemonImage>` without `size="large"`, shown at 36 to 64 px) load PokéAPI's 96 px
  sprite (`sprites/pokemon/<id>.png`, 1 to 2 KB) instead of the 512 px HOME artwork (about 130 KB). Decorative heroes
  that stretch a small image (home, page headings, trainer hero) pass `art="artwork"`. When an image fails, the
  browser tries HOME artwork, then the official artwork, then a placeholder (`src/lib/pokemon-art.ts`; the species id is
  in `data-art`, so long tables don't repeat fallback URLs). Every page preconnects to `raw.githubusercontent.com`.
- `/trainers/`: the directory ships as a plain A–Z list of profile links whose `data-*` attributes hold what a card
  shows; the page script draws 18 cards at a time from it. Battle guide cards (`<TrainerCard lite>`) leave out the team
  table and load it from the trainer's profile page when opened. `site/tests/trainers-browser.mjs` covers the filters,
  paging, loading the team and the page without JavaScript.
- Long Pokémon tables (more than 100 rows, such as a common move's learners) sit in `.long-table`, which uses
  `content-visibility: auto` so the browser lays them out only near the screen.
- Scoped `<style>` blocks add a class to every element of the component. Pages with thousands of rows (`/pokemon/`,
  `/trainers/`) use `<style is:global>` with selectors under the page's own class instead.
- `ohg.js` leaves table rows in place unless the table is sorted (re-appending 1,400 rows was the slowest part of
  loading a long table).
- Not changed: the save editor's script (1.1 MB, 270 KB compressed) is mostly its bundled game data and loads only on
  `/save-editor/`; Starlight loads the search UI when the browser is idle; GitHub Pages sets `max-age=600` on every file.

`MobileMenuToggle.astro` adds a JavaScript fallback for browsers without the Popover API
(including iOS before 17), and clears the page's interaction/scroll lock when the drawer
closes, the viewport changes, or a page is restored from history. Without JavaScript,
older browsers show navigation in the page flow so it cannot cover the content.
Test against a local production preview with existing WebKit and Chromium installations:

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs GUIDE_PREVIEW_URL=http://127.0.0.1:4338/ node site/tests/mobile-menu-browser.mjs
```

The runner checks touch navigation, restored page interaction, and JavaScript-disabled
behavior. Its missing-popover simulation does not replace testing on a physical old iPhone.

### Shareable reference browsing

Indexes use `q` for search, their select's `data-key` for each filter (for example
`type=Water&ability=2`), and `sort=5-desc` for a zero-based column and direction
(`asc` or `desc`). Filters combine with AND; pipe-separated row values match any
individual token. Multiple filterable tables on one detail page prefix each key
with the table ID, for example `holders-hidden.availability=documented`.
Invalid filter/sort values fall back to the default. Other parameters such as
`tech=1` and the fragment survive updates and Reset. Search typing pushes one
history entry per focus/edit session and replaces that entry as typing continues;
select changes, sort and Reset push distinct states. Back/Forward restores the
controls, visible rows and ordering. Reset restores original row order. All rows
and links are available without JavaScript; filtering and sorting are enhancements.

Local browser regression after a production `/poke/` build and running preview:

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/existing/playwright/index.mjs node site/tests/browser-smoke.mjs
```

`GUIDE_PREVIEW_URL` optionally changes `http://127.0.0.1:4327/poke/`. This optional
runner uses a preexisting browser/runtime, writes only ignored `work/build/website-qa/`
results and screenshots, and uses synthetic invalid save/patch input. It does not
patch a ROM. CI's dependency-free DOM regressions run through normal `npm test`;
compiled-page assertions run after the build with `GUIDE_TEST_DIST=1`.

For quest filter regression checks, run `site/tests/quest-filters-browser.mjs` with
the same `PLAYWRIGHT_MODULE` setting and `GUIDE_PREVIEW_URL` pointing at the site root
(defaults to `http://127.0.0.1:4337/`). It checks combined filters, persistence,
old preference migration, completion ticks, direct links, mobile themes and no-JavaScript tags.
Screenshots go to ignored `work/build/quest-tags-qa/`. Metadata coverage tests run with
`python3 -m unittest discover -s work/tools/site -p 'test_quest_tags.py'`.

### Original move comparisons

Move pages compare numeric stats with Pokémon HeartGold (USA), using normalized
facts in `work/tools/site/move_original_facts.json`. The optional local importer
requires the existing untouched USA ROM with CRC32 `C180A0E9`:

```sh
work/.venv/bin/python work/tools/site/move_comparisons.py --import-us-rom 'work/rom/Pokemon - HeartGold Version (USA).nds'
python3 work/tools/site/export_data.py
```

Only move IDs 1–467 are imported; record 0 and trailing records 468–470 are
excluded. The normalized file contains numeric facts and provenance, no ROM bytes
or descriptions. CI builds from generated site content and tests numeric fixtures;
it never imports the local ROM. Original target enums and no-accuracy-check
sentinels are compared by meaning. Later moves have no HeartGold baseline, so an
explicit author change can give its new value without an invented earlier value.

Project-written effect comparisons are maintained separately in
`work/tools/site/move_change_notes.json`, preserving their source and uncertainty.
Existing battle results and configured effects keep distinct evidence. The move
index’s changed filter uses the same comparisons shown on detail pages, including
explicit uncertain change notes; receiving a new TM alone is not a move change.
Full provenance and disagreements remain on `/reference-sources/`.
