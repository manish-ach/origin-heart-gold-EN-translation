# Porting the Spanish patch's advanced trainer AI: research, 2026-10-13

Question: how to extract the "advanced AI" in `advanced-ia-spanish.xdelta` and bring it into this project. This note
follows `es_patch_comparison_20261012.md`, which analysed ES rc42 from its bytes alone. Nothing was built into this
repository and nothing was committed. All ROM work happened in the session scratchpad. "Verified" means read in code,
decoded from ROM bytes or reproduced; "inferred" means reasoned from addresses or docs.

## 1. Answer

- **The patch has local source.** `advanced-ia-spanish.xdelta` is byte-identical (SHA-1 `4f5d2f1a…`) to
  `Origin_HeartGold_v4.0.3_ES_v1.0.0-rc44.xdelta` from the Spanish translation workspace (`work_es/`, a local git
  repository with no remote, not part of this checkout); rc44 is commit `dc8577c`. It holds the full AI source
  (`tools/ai/`, `tools/asm/aiselect.s`, `tools/build.py`). Its author, luisvent, confirmed on 2026-10-13 that the
  source may be reused here, which answers the earlier note's open item "ask the author" (section 8).
- **Extract it from source.** The rc44 AI rebuilds byte for byte from `dc8577c` (verified, section 4). A binary
  transplant of the AI from the rc44 ROM cannot work, because its code is linked to the Spanish build's memory layout,
  and that layout collides with our text-speed code.
- **Integration is a port, not a copy.** The C code, the hook sites and the hack functions it calls carry over as they
  are. We need to rebuild:
  - its memory placement;
  - its settings switch;
  - its ID table;
  - the vehicle that installs it (the patch registry cannot install it today).

## 2. What the advanced AI is (verified)

The Spanish build starts from our English rc3 ROM. Every address the AI depends on is a Chinese v4.0.3 address: our rc3
build changes nothing within 0x40 bytes of any of them.

| Part | rc44 placement | Size |
|---|---|---|
| Overlay 10 (vanilla's AI overlay, a 0x20-byte stub in the hack) | 0x021E4DA0. A byte copy of overlay 11 (the hack's own trainer AI, 0x12060 B) + its 0x20 B bss, then the new slot code from 0x021F6E20 (`adv_entry`, `write_action`, `decide`) | file 108,000 B; slot code 34,144 B; bss 0x9E0; 2,688 B free before overlay 14 at 0x022007E0 |
| y9 entry 10 | size 0x20 → 0x1A5E0, bss 0 → 0x9E0, static initialisers = overlay 11's | 32 B |
| ITCM code | appended to the 0x620-byte ITCM block from 0x01FF8620: `aiselect.s` (`ai_serves`, `ai_slot_select`, `ai_entry`, `ai_bag_check`), `ai_replace`, the `g_tune` table, libgcc, shared AI code | ~23.8 KB of AI code (756 B free at 0x01FFEB0C) |
| ITCM work RAM | 0x01FFEE00–0x01FFFF8B bss; fixed test records 0x01FFFF8C–0x01FFFFFF (`engine.h:23-44`) | 4,056 + 116 B |
| Main-RAM code | a new autoload section at the old arena start 0x02264920; AI part at 0x0226D4C0 (`ai_lead` first) | 24,184 B (the section also holds 35.7 KB of other Spanish features) |
| Arena words | 0x020D1A1C main arena start 0x02264920 → 0x02273340; 0x020D1A28 ITCM arena start → 0x02000000 (emptied) | 2 words |
| Hooks (Thumb BL, all overlay 14) | core: 0x02223D10 (load overlay 10 instead of 11), 0x02203736 (AI poll → `ai_entry`), 0x02203C06 (replacement after a faint → `ai_replace`), 0x022029CC (Bag deadlock guard), 0x022153C2 (lead pick → `ai_lead`). Hard-mode only: 0x02223D36 `steer_turn`, 0x0222025C `steer_action` | 7 BL |
| Trainer marks | `a/0/5/5` header byte 2: bit 0 important (453 trainers), bit 1 keep lead (129), bit 2 boss aura (208) | 514 headers |
| Settings | event flags 0x2C2 (on) and 0x2C3 (important trainers only); a Pokémon Centre NPC (script 2072 in `a/0/1/2`, an object in 24 `a/0/3/2` maps, bank 38 strings 116–131, of which 122–127 and 130 are the AI menu) | new game: off |

**Control flow.**
1. Every selection phase, `ai_slot_select` loads overlay 10 in place of 11 when the AI serves a trainer in the battle.
2. Each client's poll reaches `ai_entry`. It runs `adv_entry` for a served trainer, and otherwise overlay 11's own entry,
   which is in both images.
3. `adv_poll` (`advai.c:7958`) snapshots both sides into a heap-5 context and spreads its simulations over polls. It then
   writes the action through the engine's setters.
4. Any failed range check, an unsupported battle, or more than 20 polls hands the turn to overlay 11's AI. The battle
   always gets a legal action.

**Bindings.** The AI calls or reads about 85 fixed addresses in arm9 and overlay 14 (`engine.h:83-196`): the damage
simulation 0x02223390, the action setters 0x0220091C/0x02200960/0x02200A30/0x022009AC, `SwitchSlotOverlay` 0x02215914,
the battle root 0x02255BAC, and the type chart 0x0224DA40, among others. None of them lies inside a region an enabled
English fix declares.

**What it does for the player.** It knows the player's whole party. It values every move, switch and item by simulating
the turn and the following exchange. It vetoes moves that cannot work, switches when that pays off, and picks its lead
against the player's lead. Doubles are handed to overlay 11.

**Hidden information (verified; kept as is, section 8).**
- **Reading the committed action.** On the trainer's side the AI waits for the player's committed action. It uses it
  only when its blind prediction gave that action at least 70%, or on its own 30% draw (`advai.c:7846-7847`).
- **Foresight.** In singles it predicts the turn's random rolls from the battle RNG.
- **Steering.** With hard mode, an important trainer and singles, it may steer its own rolls once per battle.
- **No player switch.** No player-facing setting turns these off. The clean off switch is at compile time: make
  `foe_choice` return 0, which also disables foresight and steering.

**Evidence of strength** (Spanish QA, DeSmuME and melonDS interpreter only):

| Measure | Result | Source |
|---|---|---|
| Advanced vs original AI, the hack's 6v6 trainer teams | 71/80 (88.8%; 95% range 80–94%), 0 fallbacks in 1,431 decisions | `qa/rc44_rerun.md` |
| Held-out set, 240 games | 86.67% | `qa/aivsai/RC39_MERGE.md` |
| Bench, 365 graded scenarios | 97.8%; the original AI scored 83.3% on the first 114 | `qa/aibench/` |
| Property tests | 0 violations | `qa/aiprops/` |

No game with a human player is on record, and nothing has run on real hardware.

## 3. Why not a binary transplant (verified)

- **ITCM collision.** Our `text-speed` payload sits at 0x01FF8620–0x01FF8FC0 and sets the ITCM arena word 0x020D1A28.
  The Spanish code is linked to the same start (`ai_slot_select` 0x01FF8C2A, `ai_replace` 0x01FF8E14).
- **Absolute addresses.** The slot code holds 13 BLs into the Spanish ITCM code, literals for `g_tune`, and 7 literals
  plus BLs into the Spanish-only main block. That block sits behind 35.7 KB of Spanish feature code.
- **The Spanish build refuses our ROM.** `grow_arm9` asserts an ITCM block of exactly 0x620 bytes.
- **Our registry refuses the shape.** It cannot replace a whole overlay with a larger one, add an autoload section, or
  place code past `ITCM_LIMIT` 0x01FFA000 (`fixes.py:181-188`, `toolchain.md:126`).

## 4. Extraction: what was reproduced

**Byte-identical rebuild.** `git archive dc8577c work_es/tools …` went into the scratchpad. Importing that `build.py`
runs its `link_ai()`, and each output was compared with the rc44 ROM:

| Rebuilt piece | Result |
|---|---|
| Overlay 10 image | identical |
| y9 entry 10 | identical |
| ITCM code | identical |
| Main-RAM block, including the AI part | identical |
| All 143 hook and arm9 patch entries | match the ROM |

Toolchain: arm-none-eabi-gcc 16.2.0, GNU ld 2.47.

**Compiler check.** The AI unit (`advai.c` + `replace.c` + `lead.c`) was compiled with the Spanish flags, before
`--gc-sections`:

| Compiler | Result | `.text` size |
|---|---|---|
| gcc 16.2.0 | builds | 81,249 B |
| Apple clang 17 (this machine), `-Os` | builds: 0 errors; ignores the `noipa`/`optimize` attributes it uses | 103,492 B (+27%) |
| Apple clang 17, `-Oz` | builds | 94,466 B (+16%) |

Our pinned compiler is Apple clang 21 (`toolchain.md:32,143`); it was not available here. With only 2,688 B free in the
overlay slot and 756 B in ITCM, a clang build does not fit the Spanish layout. This is the main argument for pinning
gcc for this module.

**Extracting the core means taking:**
- `tools/ai/{advai.c, engine.h, lead.c, replace.c, tune.h, link.ld}`;
- `tools/asm/aiselect.s`;
- `check_flag` from `hardmode.s`;
- `build.py`'s `link_ai`/`resident_sections`/`ai_ids_header`;
- `tools/trainers/important.py` for the marks.

Two pieces need porting rather than copying:
- **The steering externs.** They live in `steer.s`, so stub them when hard mode is not ported.
- **The ID table.** `AI_IDS` (`build.py:1741`) resolves moves, abilities and items by our old rc3 English names
  ('StompngTntrm'), which our modern glossary no longer uses. Replace it with numeric IDs. Test: the generated `ids.h`
  equals the Spanish one.

## 5. Constraints in this project (verified)

- **Registry.** armips v0.11.0 applies every fix. `.create` and file creation are refused, overlays grow at most
  0x1000 B by appending, and an overlay with bss cannot grow. ITCM may only be appended to, up to 0x01FFA000, which is
  text-speed's budget and not a hardware limit. The only native-code precedent is text-speed: pinned clang, no linker.
- **Difficulty installer.** Difficulty (D-2301) ships through a separate installer that runs after the build
  (`work/research/difficulty-armips/install.py`). It:
  - pins the input ROM SHA, the whole-file SHA of arm9, ITCM (exactly 4,032 B) and overlays 9, 14 and 50, and the
    arena low 0x02264920;
  - adds a 4th autoload section at 0x023DC000–0x023E0000, with 6,324 B used;
  - lowers the arena-high literal at 0x020D1970.

  Any AI hook in overlay 14 or change to ITCM breaks those pins and needs a compatibility re-pin
  (`rc8_difficulty_compatibility_20261013.md` is the model).
- **No overlaps.** No English fix overlaps the 7 hook sites; the nearest is battle-party-status-sync at 0x02203DC6.
  The AI calls functions our fixes changed, e.g. near `zero-pp-struggle`'s guards at 0x02200960/0x0222C304. That is a
  behaviour difference to test, not a byte collision.
- **Flags.** Flags 0x2C2 and 0x2C3 appear in no English patch or research file (grep). The settings live in the Options
  halfword (text speed bits 2–3; difficulty mask 0x8028). Whether a spare bit exists for an AI switch is not verified.
- **Overlay 14 cannot grow** (it has bss). The overlay-10 slot ends at 0x022007E0.

| Scope | The AI core with replacement and lead, nothing else (section 8). No steering (we have no hard mode), no battle-experience lines, no aura, no VS intro, no NPC. Off by default (D-1575 optional feature) |
| Source | Vendor the files listed in section 4 into a feature tree, e.g. `work/native/advanced-ai/`, with a `PROVENANCE.md` naming the Spanish commit `dc8577c` (decided: `work/advanced-ai/`, see its README) |
| Golden test | Before any change, the vendored sources built with the Spanish layout parameters must reproduce rc44's overlay 10, ITCM and main AI bytes. This proves the extraction is faithful |
| Toolchain | Pin arm-none-eabi-gcc and binutils for this module (version-checked like the clang pin), because of size (section 4). The alternative is clang plus moving ~13–22 KB more code to main RAM |
| Overlay 10 | Same shape as rc44: the Chinese overlay 11 copy + slot code; y9 entry 10 rewritten |
| Resident code (~24 KB ITCM + ~24 KB main + 4 KB work RAM) | **Option A:** ITCM after text-speed, from 0x01FF8FC0. This roughly fits once the Spanish non-AI ITCM asm (~1.8 KB) is left out; to be confirmed by a link. It requires proving the SDK ITCM arena is never allocated in our build (the Spanish build's docs say so; not measured here), and then raising `ITCM_LIMIT`. **Option B:** main RAM, by growing difficulty's arena-high reservation below 0x023DC000 by ~32–48 KB; this costs main heap, and English text already presses the heap. Decide after measuring both: an ITCM-arena allocation watch and main-heap headroom on battle, Bag, party and summary screens |
| Hooks | The 5 core overlay-14 BLs above. `ai_replace` and `ai_lead` are optional but part of the measured strength |
| Trainer marks | A narc fix on `a/0/5/5` header byte 2, bits 0–1, generated by the ported `important.py` (verify again that the hack's engine ignores byte 2) |
| Setting | A row on the Options page next to the difficulty settings (OFF / BOSSES / ALL) that drives `ai_serves`; no NPC (section 8). Store it in a spare Options bit if one exists, or else in flags 0x2C2/0x2C3, as the Spanish build does |
| Vehicle | First as a post-build installer combined with difficulty's (one native installer, one set of pins). Then extend the registry with an "overlay replace" and "autoload section" kind, which difficulty also needs before it can leave `work/research` |
| Worktree | `~/Developer/poke-advanced-ai`, branch `feature/advanced-ai`, merged disabled, like the hack-bug fixes |

**Release gates** (D-1575: own gates plus emulator checks on a fresh build):
1. The golden test.
2. The host-build simulator (`tools/sim`, `tools/hostai`: plain C, no emulator) running against our ROM data.
3. AI off: our current emulator suite and the difficulty native tests pass unchanged.
4. AI on: an 80-game AI-vs-AI run within the Spanish 95% range, 0 fallbacks, 0 property violations, and every setting,
   doubles and partner case (`aimode_check` equivalent).
5. Heap headroom on English text.
6. melonDS interpreter.
7. One real-hardware smoke test (flashcart). Neither project has done this.

The Spanish emulator tools (`aivsai`, `aiprops`, `aibench`, `lead_check`) need DeSmuME exec hooks. Our harness has
them on DeSmuME but not on melonDS. Port them as a package with their own runner, plus English winner strings and
English pre-battle saves.

## 8. Answers (luisvent, 2026-10-13)

Not yet in the decision register: the register records the project maintainer's decisions.

1. **Reuse.** Yes: the Spanish workspace's AI source may be reused. This clears the licence blocker in
   `es_patch_comparison_20261012.md` §1 and §7.
2. **Scope.** The AI core only. Nothing else from the Spanish build is ported for now (no battle-experience lines,
   VS intro, aura, steering, hard mode or NPC).
3. **Hidden information.** Keep the Spanish behaviour: it reads the committed action with the 70%/30% gate and uses
   foresight. This is the only configuration measured as shipped; limiting the read cost 74/80 → 68/80 in rc33.
4. **Setting UI.** An Options row; no NPC.
5. **Toolchain.** gcc, pinned (decided after the explanation below). The plan is `work/advanced-ai/PLAN.md`.

**Why gcc.** The same source and flags give 81 KB of code with gcc and 94–103 KB with clang (section 4).
- The Spanish layout has 2.7 KB free in the overlay slot and under 1 KB in ITCM. A clang build therefore needs another
  13–22 KB of resident main RAM, on top of the ~24 KB already planned, and English text already presses the heap.
- Every measurement (strength, fallbacks, decision time) is of gcc's output.
- The link step that splits the code between ITCM and main RAM is written for GNU ld.

**Why pinned.** This is the project's existing rule for native code, not a new one for gcc. Text speed pins Apple
clang 21 because "another clang may produce other bytes" (`toolchain.md:143`). The release gate `check.py --repro`
recompiles native code from source and requires identical bytes. A different gcc version would ship untested bytes,
and with 2.7 KB of slack it could overflow the slot.

**Cost.** Following text speed's model, the reviewed compiled output is committed, and normal builds use it with no
compiler at all. Only someone who changes the AI, or runs the release repro check, needs the pinned arm-none-eabi-gcc
16.2.0 and binutils 2.47 (the versions that built rc44). The pin turns a silent Homebrew upgrade into a clear error.

**Alternative.** Use the project's clang, and accept the extra main RAM or trim code. Then re-run the strength and
fallback tests, because the bytes are new.
